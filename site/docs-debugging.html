Attach GDB

The emulator ships a GDB Remote Serial Protocol stub (pkg/gdbstub.mjs, published as stm32f1-emu/gdb). Any ARM-aware GDB attaches over TCP:

import { serveGdb } from 'stm32f1-emu/gdb';
const srv = await serveGdb({ firmware, chip: 'gd32f103c8', port: 1234 });

$ arm-none-eabi-gdb -ex 'target remote :1234' firmware.elf
(gdb) break loop
(gdb) continue        # stops at the breakpoint (SIGTRAP)
(gdb) info registers pc sp
(gdb) x/8xw $sp
(gdb) stepi
(gdb) detach

A complete scripted session lives in tests/gdb_live_session.sh (needs the Arduino toolchain's arm-none-eabi-gdb); tests/test_gdbstub.mjs drives the same protocol with a synthetic client in CI.

How breakpoints work

Breakpoints are 16-bit BKPT patches. The core faults loudly on them, and the stub tells a hit apart from a genuine decode gap by address: on a hit it restores the original instruction, resumes at it, reports SIGTRAP, single-steps the original on resume, and re-inserts the patch. Anything else reports SIGILL and halts. Flash patching uses a probe-style raw write path — normal guest stores respect flash protection.

Fidelity notes

  • Single thread; 17 core registers (r0–r12, sp, lr, pc, xpsr) — no FPU on M3.
  • s steps one thread instruction plus any domestically-pending IRQ service for that batch.
  • Breakpoint addresses are masked to halfwords (Thumb); Ctrl-C halts a running continue.
  • Symbols stay in GDB (load the ELF there); the stub runs symbol-free so faults surface instead of escalating.

Without GDB

The demo page shows live PC/SP, instruction counts and a UART terminal; load a .map after the firmware for PC → symbol names. Headless, pkg/cli.mjs --regs --verbose traces execution. Full reference: docs/GDB.md.
